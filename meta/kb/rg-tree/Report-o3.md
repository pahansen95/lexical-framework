# Red-Green Tree Architecture and Modern Syntax Tree Implementations

## Executive Summary

**Overview:** Modern compiler and IDE frameworks often use *immutable, persistent syntax trees* to represent source code. A prominent example is the **Red-Green tree architecture**, first introduced in Microsoft’s Roslyn (C#) compiler and since adopted or adapted in Swift’s compiler infrastructure and Rust’s analysis tools. In a Red-Green tree, **two parallel tree structures** represent the code: an *immutable “green” tree* that holds the complete concrete syntax (including all tokens and trivia) and supports *structural sharing* (reusing unchanged subtrees after edits), and a *“red” tree* of wrapper nodes that provide *parent pointers, absolute positions, and a user-friendly API*. This design resolves the tension between immutability and efficient navigation by separating concerns into two layers. The green tree is the truth of the code’s text, and the red tree is an ephemeral facade for convenient traversal. Together, they enable *incremental updates* (reparsing only affected regions on edits) and safe concurrent reads, at the cost of additional complexity and memory overhead.

**Key Findings:** Red-Green trees provide *excellent support for interactive editing* (as in IDEs) by allowing most of an unchanged tree to be reused after a text edit, typically rebuilding only *O(log n)* of the nodes around the edit. They ensure **immutability** (no surprises from in-place mutations) and thus inherently support *thread-safe concurrent reads* (no locks needed for reading an immutable tree). However, the dual-tree approach can nearly **double the number of objects** in memory versus a traditional mutable AST. This increases GC pressure in managed languages, leading implementers to introduce optimizations like interning common tokens and even using value types for tokens (in .NET) to cut down allocation counts. Variations of the red-green pattern (such as those in Rust’s `rowan` and `cstree` libraries) demonstrate that performance trade-offs can be adjusted – for example, by *caching or persisting the red nodes* to speed up repeated traversals or by interning strings and node data for memory efficiency.

**Alternative Approaches:** We surveyed other tree implementation strategies:

* *Pure persistent trees:* Fully immutable ASTs (without a separate facade) rely on **structural sharing** – new versions share unchanged parts with old versions – to avoid full copies on modifications. This can achieve similar benefits to red-green trees (incremental updates, immutability) with less scaffolding, but typically they do **not store parent pointers or absolute positions** in nodes (to avoid expensive updates on every small edit). Navigation up the tree or mapping nodes to source positions then requires computation (or separate indexing structures), which can complicate usage.

* *Zipper data structures:* A *zipper* is a technique to focus on and update a part of an immutable tree efficiently by carrying a cursor (focus node) and its context. It essentially treats the tree as “cut open” at the focus, enabling localized, in-place-feeling edits without global copying. Zippers make functional updates *O(1)* at the focus and allow moving the focus around cheaply, but they are more of an editing utility rather than a standalone tree representation. They shine when implementing editor-like transformations on immutable trees, though by themselves they don’t provide structural sharing beyond the focus (they are a means to construct a new persistent tree version efficiently).

* *Traditional mutable ASTs:* Many compilers (and older IDEs) use a simple **mutable syntax tree** where nodes have parent pointers and children, and the tree can be directly modified. This approach is memory-efficient and straightforward (no duplicate structures). However, it lacks persistence: making an edit typically mutates or rebuilds the tree in-place, *invalidating any previous tree state*. Incremental updates in such systems require custom logic to patch the tree, which can be error-prone. Concurrency is also harder – you must ensure no thread is reading the AST while another is modifying it. Despite these drawbacks for interactive use, mutable ASTs remain popular for single-pass compilers due to their speed and simplicity (no extra indirection layers or cache misses from pointer-heavy immutable nodes).

If the use case is a one-shot compiler or a simpler transform tool (where the code is parsed once and then processed), a traditional mutable AST or a simpler persistent tree might suffice and be easier to implement. In summary:

## Red-Green Tree Architecture and Mechanics

**Concept and Motivation:** The Red-Green tree architecture addresses a set of seemingly conflicting requirements for compiler syntax trees: (1) immutability (for safety and sharing), (2) efficient *persistent updates* (reuse of unchanged parts on text edits), (3) parent-pointer navigation from any node, (4) the ability to map any node to its exact location in the source text, and (5) a tree structure faithful to source (including all tokens/trivia). Achieving all of these in a single data structure is non-trivial – for example, storing parent links or absolute character positions in an immutable tree complicates persistence, since a small edit could otherwise force updating many nodes’ parent or position fields. The Roslyn team solved this by splitting the responsibilities between two coupled structures:

* **Green Tree (Immutable Concrete Syntax):** The green tree represents the source code’s full concrete syntax (often a *concrete syntax tree* including all tokens and even whitespace/comments). **Green nodes are fully immutable and have no pointers to their parents**. Each green node is created *bottom-up* (children first) and stores its *local syntactic information* (such as the kind of node/token and the list of children) as well as the *cumulative width* of the subtree (the number of characters covered by that node’s text). Notably, a green node does **not** know its absolute position in the file – only how wide it is. Nor can it directly access siblings or parent. This isolation makes green nodes highly reusable: if two parts of the code are identical, they can literally use the same green subtree object, and when code is edited, any unaffected subtrees can be *reused verbatim* in the new green tree. The green tree is thus a classic *persistent data structure* – old versions can co-exist with new, sharing most of their nodes. In practice, Roslyn’s implementation interns identical green nodes to maximize reuse: e.g., every occurrence of the same keyword or punctuation token can point to a single shared green token node in memory. In fact, for each lexical token that’s known in advance (such as the `if` keyword, a semicolon, etc.), Roslyn pre-creates a handful of *cached green nodes* (covering common trivia scenarios like “no whitespace”, “trailing space”, “trailing newline”, etc.) so that the parser can just reuse those without new allocations. This aggressive deduplication means that *with \~95% probability, any given keyword token in source is represented by an existing interned green node* – a huge memory win in large projects with many repeats of keywords and symbols.

* **Red Tree (Immutable Facade with Parent/Position):** The red tree is a *wrapper layer* that gives the green tree “legs” to stand in an API. **Red nodes are what the end-user (or analyzer) interacts with** when using the syntax tree API. Each red node wraps a green node and knows its **parent (red) node**, as well as the **absolute position** of that node in the source text. In other words, red nodes are augmented with exactly the information that green nodes omit. Crucially, red nodes are created *on demand* and in a **lazy, top-down** fashion. When a syntax tree is initially produced, you get a red *root* node that wraps the green root; but none of its children have red wrappers yet until you ask for them. If you traverse the tree (say, requesting the first child of the root), the red `GetChild` method will wrap the corresponding green child in a new red node, set its parent pointer to the current red node, compute its absolute start position by adding up widths on the path, and return it. That new red node might be cached inside the parent red node for later reuse. In Roslyn’s case, red nodes *present an immutable interface* but internally they may cache these child references after creation (the first time you access a child, it saves the red child in the parent). This caching means subsequent traversals don’t constantly recreate new red objects; effectively, the red tree can “materialize” as much as needed for the portion of the tree you explore, while portions you never touch remain just green. Importantly, the entire red tree is **rebuilt on any edit** to the source – but not eagerly. When the source changes, Roslyn discards the old red tree (or portions of it) and produces a new red tree *only when the API consumer requests it* (and even then, typically only for the new/changed parts). The green tree, by contrast, is updated minimally under the hood (sharing most nodes with the pre-edit tree) so that when you do request a new red tree, it can wrap large swathes of reused green structure without new parsing work.

**Diagram – Red vs Green:** *In a simplified illustration, imagine a tiny expression `1 + 1`. The green tree might have a root node for the binary expression with three children (green tokens for `'1'`, `'+'`, `'1'`). These green tokens have no parent pointers and just store their text and width (1 character each). The green root knows it has 3 children and total width 3. When exposed via the red API, a red `BinaryExpressionNode` wraps the green root. It has pointers to its red children: asking for `LeftOperand` creates a red node wrapping the first green `'1'` token, with parent set to the binary expression node and position 0. Similarly, `Operator` yields a red node for `'+'` at position 2, etc. The red nodes allow you to navigate up/down easily and get absolute positions, while internally they defer to the shared green nodes for syntax details.* (This example corresponds to how identical green tokens could even be shared if another part of the code had a `1 + 1` expression – both plus tokens could be the *exact same object* in the green tree, though each appears at different positions via distinct red wrappers.)

**Immutability and Thread Safety:** Both red and green nodes are *immutable objects*. Once created, a node’s content (and its green subtree) never changes. Any operation that would “modify” a tree (e.g., inserting a node, changing a token) is defined to produce a *new tree/node* value, rather than mutate in place. This immutability yields *referential transparency* (a given syntax node will always represent the same source substring) and trivially enables *safe concurrent access*. Roslyn was designed so that multiple threads could safely read the syntax tree (red or green) without locks. In fact, some implementations go further: the Rust `cstree` library (inspired by Roslyn/Swift) makes its syntax nodes thread-safe (`Send` and `Sync` in Rust terms) by using atomic reference counting on the whole tree, allowing *sharing realized red trees across threads* with no cloning. This is particularly useful for language servers that might parse once and then let multiple analyzer threads query the tree concurrently. Red-Green’s immutability also simplifies undo/redo or speculative analysis: since old trees aren’t destroyed by edits (the green nodes can persist as long as they’re referenced), an IDE can keep pointers to previous versions or subtrees (e.g., to highlight a diff) without defensive copying.

**Incremental Parsing and Persistence:** A major advantage of the green tree design is efficient **incremental updates**. When the source text changes (e.g., the user types a character), the parser can avoid re-parsing the entire file. Instead, it *lexes and parses only the affected portion* and then produces a new green tree that *reuses* all unaffected parts of the previous tree. For example, if you insert a character inside a function, only that function’s subtree might need re-parsing; the rest of the file’s green nodes can be reused as-is. Roslyn’s parser is equipped to do this: given the old tree and a text diff, it finds the smallest syntax sub-tree that encloses the edit and reparses that, then stitches it back in, keeping other nodes unchanged. The complexity of this can be as low as *O(log n)* relative to the file size for small localized edits. The result is a new green tree. Because of immutability, the old tree remains intact (which could be used for undo or debugging), and the new tree mostly points into the old tree’s nodes for shared parts. The new red tree (if and when created) will be a fresh facade, but creation is lazy and typically only *partial*: for example, an IDE’s semantic analyzer might only traverse the method that changed, creating red nodes in that area, leaving other methods’ red nodes unmaterialized. This strategy dramatically reduces the work on continuous edits; indeed it’s what allows modern IDEs to reparse on every keystroke without freezing. As Eric Lippert noted, **persisting nodes across edits was essential for performance**, otherwise “we \[would] be re-parsing huge wodges of text every time you hit a key”.

**Cost and Memory Considerations:** The benefits of Red-Green trees come with costs. The primary cost is **memory usage** and increased GC load. Each syntax element is represented by at least one green node *and* one red node (the red being ephemeral). Lippert observed this scheme “ends up creating up to twice as many small objects as a normal parse tree would”. All those objects put pressure on the garbage collector – especially since the red nodes are short-lived (they are thrown away and rebuilt on edits) while green nodes may be long-lived (persisting across many edits). This mix of short-term and long-term objects can be pathological for generational GC, as it can “produce the worst case for data locality while maximizing the work the compacting collector must do”. In .NET, the team measured these effects carefully and introduced mitigations. One major optimization: making **`SyntaxToken` a value struct** in the red model. In C# source, roughly half the nodes in a full syntax tree are leaf tokens (identifiers, literals, punctuation). By making tokens value types (structs) rather than objects, Roslyn eliminated a huge number of object allocations and GC overhead. The green tokens are still reference types (for interning), but red tokens can be lightweight structs referring to green token internals. Another optimization in Roslyn’s red layer is the use of **weak references** for caching red nodes. Red nodes that aren’t in use by any external code can be garbage-collected, even if their parent red node is still around (the parent holds only a WeakReference to them). This means the red “facade” can scale in memory according to usage: if an analyzer only touches a small part of the tree, other parts might never be realized as red nodes; or if they were realized once but not used again, they don’t need to stick around in memory forever. They can be regenerated from the green tree later if needed. This approach addresses the concern Lippert mentioned that the red facade “can consume a lot of memory if \[it] gets large” – by making the caching of red nodes opportunistic and memory-friendly.

**Performance Characteristics:** In terms of speed, red-green trees can be very fast for certain operations and slower for others, compared to a traditional AST. *Tree navigation* (reading parent/child relationships) through the red API is quite efficient – typically just pointer dereferences and simple arithmetic (adding child offset to parent’s position to get absolute position, etc.). If the red tree is fully materialized, traversals are comparable to any in-memory object graph traversal. If the red tree is not fully materialized, the first traversal that touches new parts will incur the cost of wrapping green nodes in red objects. That’s additional overhead not present in a pre-built mutable tree, but in practice these costs are amortized, and Roslyn’s lazy approach ensures you pay only for what you use. Subsequent traversals can often reuse the now-cached red nodes (at least until the next edit). One area that needed attention is *traversing very large node lists* (e.g., a huge method body with thousands of statements). Roslyn employs specific optimizations here: for example, in lists of children beyond a certain length, it precomputes a **prefix sum array of children widths** so it can map a character offset to the child index in O(log N) time rather than scanning linearly. This improves performance for finding the corresponding node for a position in large lists (like quickly determining “what statement is at line 5000?” without visiting every prior statement). The immutability of green nodes also opens up possibilities for *bit-level optimizations*: Roslyn packs small boolean properties and enum discriminators into bits in the node objects to keep them compact. The result of many such tricks is that, despite having more objects, the overall memory footprint is kept “extremely compact” for the functionality it delivers.

**Summary:** Red-Green trees provide a robust solution for maintaining **lossless syntax trees** (including all source text) in an interactive environment. They partition the problem: a minimal, sharable “green” representation of syntax, and a richer “red” view for consumers. This yields *powerful invariants* (trees are always immutable and consistent) and enables advanced features (incremental parsing, multi-threaded analysis) at the cost of a more complex implementation under the hood. The design is now proven in large scale: Roslyn’s trees keep the Visual Studio IDE responsive even in projects with millions of lines of code by updating and reusing syntax nodes efficiently between keystrokes. Many modern language tooling projects have either adopted this pattern or drawn inspiration from it, as we will see in case studies.

## Alternative Approaches to Syntax Trees

While red-green trees are a state-of-the-art solution for interactive use cases, it’s important to consider other data structure patterns for syntax trees, each with their own trade-offs. Here we explore several alternatives: pure persistent trees, functional zippers, and traditional mutable ASTs (including variations like copy-on-write and flat data structures).

### Persistent Functional Trees (Single-Tree Immutability)

A *persistent* data structure is one that preserves previous versions when modified. In the context of syntax trees, a **persistent AST** would mean that each edit produces a new tree, but the new tree shares all unchanged parts with the old one (this is often called *structural sharing*). This is essentially what the green tree in a red-green setup does, but here we consider doing it with just one kind of node (no separate facade).

**How it works:** In a persistent AST, all nodes are immutable. To “modify” the tree (say, insert a node or change a token), one would create new nodes along the path from the modification point to the root, reusing the existing subtrees that weren’t changed. Only the ancestors of the edited location are new; everything else can be shared. For example, in a binary tree, inserting a new leaf would require creating a new parent node pointing to that new leaf and reusing the other child pointer from the old parent, and so on up to the root. The entire original tree remains intact (allowing you to, for instance, compare two versions or roll back easily), and the new tree largely consists of pointers to the old tree’s nodes plus a few new nodes along one path.

**Advantages:** This approach provides *many of the same benefits as red-green trees* in terms of immutability and reuse. Any previous version can still be referenced; thus features like undo or diffing two states are naturally supported. Multi-threaded readers are safe since no thread will see an inconsistent partial update – the old and new trees are separate objects that share parts but are individually frozen. Memory efficiency is gained via structural sharing: large subtrees that are unchanged between versions aren’t duplicated. For instance, if you have a 10,000-node AST and you change one node, a persistent structure might only create a handful of new nodes (perhaps the edited node and each of its ancestors), and the other \~9,990 nodes are just reused from the old version. This can be highly efficient if changes are localized.

**Challenges:** The trickiness comes with features like parent pointers and absolute positions. If every node is immutable and shared, storing a direct parent reference or an absolute source offset in each node becomes problematic – those are exactly the pieces of information that *do* change if the node’s context changes. For example, if we inserted a new statement at the top of a function, all the following statements’ absolute positions shift by some number of characters. In a persistent tree that stored absolute offsets in each node, that one insertion would effectively require copying and updating the offset in every subsequent node – negating the benefits of structural sharing. This is why persistent trees typically avoid storing global positions; instead, one computes positions as needed (e.g., by summing widths like Roslyn’s green nodes do). Similarly, without a parent pointer, algorithms that need to go from a node to its parent either have to maintain a separate stack during traversal or use an auxiliary map from node to parent (which itself must be carefully managed since nodes can be shared in multiple parent contexts theoretically). Many persistent AST implementations simply do *without* parent pointers and accept a slightly more complex traversal when moving upward.

Another consideration is *garbage collection:* in a GC language, persistent data structures rely on the GC to eventually reclaim old versions that are no longer referenced. In systems without GC (or in lower-level languages like C++), one might need to do manual reference counting or a copy-on-write scheme to manage memory, since an old tree could otherwise leak memory when it’s superseded by a new one. For instance, LLVM’s Clang uses a mutable AST and doesn’t try to persist old versions – it opts for rebuilding on changes – partly because C++ lacks automatic garbage collection to gracefully drop old tree pieces.

**When to use:** A persistent single-tree AST can be a good fit if you want *simplicity over maximal performance*. It’s conceptually simpler than maintaining two parallel structures (like red-green) and might be easier to implement in a functional programming style (many functional compilers do exactly this, representing ASTs as algebraic data types that are rebuilt as needed). It works best if parent relationships and absolute positions can be computed on the fly or handled via external lookup when needed. For example, a functional language compiler might never need parent pointers in the AST if the semantic analysis naturally carries context as it traverses. If needed, one can always augment a persistent AST with a zipper or with on-demand calculations for offsets (e.g., by accumulating position in recursive functions). The bottom line: persistent ASTs offer *immutable safety* and *incremental updates* with potentially less overhead than red-green, but may require sacrificing some direct conveniences (like constant-time parent navigation or pre-computed node positions).

### Copy-on-Write and Rope-Like Variations

A related pattern to persistent trees is **copy-on-write** (COW). In a copy-on-write approach, you treat the data structure as immutable and copy parts only when a write (modification) occurs. This is essentially what persistent structural sharing does, but the term “copy-on-write” is often used in contexts where the data might normally be mutable but is being treated in a functional way for certain benefits. For syntax trees, one could imagine a copy-on-write AST: on an edit, you copy the path to the root as needed (making new nodes) and reuse others. This is just another way to describe a persistent update. Some systems might use copy-on-write with *reference counting*: each node knows how many trees (versions) are currently using it, so that it can be freed when no tree refers to it. This is an approach taken by some C++ libraries for persistent data structures.

Another variation is using **ropes or piece tables** (used for text editors) – these are usually for strings rather than parsed trees, but the concept is similar: you keep pieces of an object and only adjust the pieces around an edit. A piece-table representation for source could, for example, hold the code as a sequence of spans from an original and an edit buffer. While this is more about text, not syntax trees, it underscores a general approach: *avoid rewriting everything; just point to old pieces plus new pieces.* The AST analog is structural sharing as we discussed.

### Zippers for Tree Editing

The **zipper** is a classic functional programming technique that is highly relevant when working with persistent trees. As described earlier, a zipper is essentially a pair: *(focus, context)*. When you focus on a particular node in a tree (the “zipper position”), the context contains the information needed to reconstruct the whole tree with that focus potentially modified. In simpler terms, a zipper provides a way to turn a tree into a structure that you can navigate *and update* like a cursor.

**How a zipper works:** For a tree, a zipper might be represented by a tuple `(node, path)` where `node` is the current focused node (subtree) and `path` carries the parent’s left siblings, parent node info, and parent’s right siblings (this is one typical encoding). Moving the focus down into a child means pushing the current node onto the path stack; moving up means popping from the stack and reassembling the node into its parent context. Because the tree is immutable, “reassembling” actually creates new nodes on the way back up – effectively this yields a new version of the tree if a change was made at the focus.

**Efficiency benefits:** The zipper allows *localized mutations* in a persistent setting without having to manually thread through all the recursion. For instance, if you want to update a deeply nested node, you can navigate to it with a zipper (which gives you O(depth) traversal cost), then perform an update (which conceptually just replaces that node), and then “zip” the tree back up – which will create new parent nodes along that path, sharing everything else. This is exactly what you’d do manually with structural sharing; the zipper just provides a convenient mechanism to do it. The key point is that *while the zipper is focused on a node, that node is treated as the “current” structure and the rest of the tree is in the context.* You can think of it like “the tree with a hole in it” at the focus point. Because of this, **inserting or deleting at the focus is O(1)** (just change the focused node or replace it), and moving the focus one step left/right/up/down is also O(1) (just reassign pointers between the focus and context) – all these operations create new persistent structures, but only along the small area of change.

**Trade-offs:** One might wonder, why not use zippers for everything? The challenge is that a zipper is a *momentary view* of a tree, not the tree itself. It’s great for implementing algorithms that need to traverse and make edits, because it gives you a sort of in-place feel. But at the end of the day, you still produce a new tree result after the zipper operations and pass that around. In the context of an IDE, a zipper might be used internally for say, applying a complex refactor (traversing the tree and rewriting certain nodes). But the persistent tree could be updated with or without an explicit zipper; the zipper just makes the code cleaner.

Another limitation is that zippers *don’t inherently support efficient persistence of multiple versions* beyond the one you’re working on. If you want to keep every intermediate state you get while moving the zipper, you would essentially collect all those versions. Usually, you just care about the final rebuilt tree. So zippers complement persistent trees; they are not an alternative representation so much as a technique to manipulate an immutable representation efficiently. They shine in purely functional languages for writing tree transformations. In an OO setting like Roslyn (C#), similar patterns can be achieved by explicitly writing tree rewrite methods that carry along parent info, etc., but the zipper concept as a first-class structure isn’t as commonly used in OO libraries. There are libraries in various languages that implement zippers generically (even a Python example exists demonstrating zippers for Python ASTs).

**Summary:** The zipper is *useful for implementing fine-grained edits* on an immutable tree. If one were not using a red-green scheme, but still wanted to handle user edits, one approach is: parse into a persistent AST, then use a zipper to navigate to the edit location, change it, and produce a new AST. This could be efficient if the edit location can be quickly found (e.g., via a node index or by traversing from root). However, in practice, parsers often do the job of integrating edits more directly (reparsing, which is effectively what Roslyn does rather than manually splicing trees). So zippers are more often seen in transformation tools and functional language compilers than in industrial IDE parsers.

### Traditional Mutable ASTs

Before the prevalence of immutable trees, most compiler ASTs were simply **mutable object graphs**. Each node object has fields for its children and maybe a pointer to its parent or enclosing scope. The parser builds the tree in place (often top-down or bottom-up depending on the parser). Later compiler stages might annotate nodes with information (type information, symbols, etc.) or even modify the tree (for desugaring or optimization).

**Characteristics:** The mutable AST is straightforward and usually memory-optimal: each piece of syntax is one object, linked directly. Parent pointers can be set during construction to allow navigation in both directions. Absolute positions (offsets) can be stored in each node at parse time if needed, or computed when asked by walking from the root with a counter. Since everything is modifiable, passes that need to change the tree (like constant folding, or macro expansion) can just do so in place, without allocating new nodes (in contrast, in an immutable model, such transforms produce new trees or new subtrees). There’s no overhead of maintaining old versions or wrappers.

**Performance:** For batch compilers, mutable ASTs are often faster and use less memory than persistent ones because they avoid the indirections and additional bookkeeping. For example, a C compiler parsing millions of lines might prefer to allocate AST nodes in arenas (contiguous memory pools) for speed and locality, and it will free them all at once when compilation is done. That approach can be extremely cache-friendly (linear allocation) and avoids GC overhead entirely (just free the arena). This is a pattern in compilers like GCC and Clang: parse into an arena-allocated AST, use it, then destroy.

**Problems in interactive use:** The trouble comes when you want to support *incremental updates or concurrency*. A mutable AST represents one state of the code. If the user edits the code, you have to somehow reflect that in the AST. There are a few options:

* One is to throw away the old AST and parse a new one from scratch (simple but potentially slow for large files).
* Another is to perform an incremental update: find the edited region and mutate the existing AST to match the new code. Some IDEs have historically done this with varying success. It requires carefully adjusting not only the structure at the edit point, but also updating parent nodes’ positions, and possibly rechecking consistency. It’s doable for localized edits (e.g., inserting a token in a token list), but very tricky if the edit changes the grammar shape (you effectively need a parser anyway to figure out the new structure).
* Yet another approach is to hybridize: use a mutable AST but leverage external incremental computation. For instance, JetBrains IntelliJ IDEA uses PSI (Program Structure Interface) trees which are a kind of mutable AST for code, but they integrate with a *reparse on change* mechanism. When a small edit occurs, IDEA will often reparse a certain range of text into a miniature AST and then graft it into the existing PSI tree, replacing the affected nodes. The PSI nodes are mutable and support operations like `replaceChild`. This gives an effect similar to structural sharing (only parts are changed) but it’s managed imperatively. The downside is ensuring the operation is safe and leaves the tree in a valid state.

Another issue is *multi-threaded read/modify*: if one thread is analyzing the AST while another modifies it (say, in a background thread), you need locks or versioning, otherwise the analyzer can crash on a half-updated tree. Many environments avoid true parallelism here by funneling all edits and analysis through a single thread or by using snapshots (e.g., copy the AST for analysis while another version is being built).

**Use cases:** Despite these drawbacks, mutable ASTs are fine in contexts where you don’t need to keep old versions or thread-safety. For example, a one-time compiler doesn’t need to preserve the pre-optimized AST after it moves on to machine code generation. Or a simple scripting engine might recreate the AST on each run and not care about persistence. The mutable approach also makes attaching metadata straightforward – you just add fields or properties on the nodes (like a type field that gets filled in later, or pointers to symbol table entries). This is convenient and efficient; in an immutable model, you can’t directly attach such info without violating immutability (instead you’d keep side-maps from node to info, which is a bit indirect).

**Memory and caches:** A mutable AST can be augmented with caches as well – for example, a node might lazily compute something (like a hash of its subtree for incremental compilation) and store it, updating it when children change. This is something persistent models can’t easily do (or if they do, the cached value becomes stale if the node is reused in a new tree version). So there’s a potential performance edge for mutable structures in maintaining auxiliary info.

**Conclusion on mutable ASTs:** They represent the classic time-space trade-off reversal compared to red-green: minimal space and simple time model (just do things in place), but any sophisticated incremental or parallel usage must be carefully built on top. In modern IDE development, most trends favor immutable approaches because they make it easier to reason about state and avoid hard-to-track bugs. However, the success of IntelliJ’s platform (largely using mutable PSI trees with careful incremental reparsing) shows that with enough engineering, a mutable approach can deliver good interactive performance too. It’s just a different balance of complexity: where Roslyn puts complexity in the data structure (dual trees, lazy computation, etc.), IntelliJ puts complexity in the incremental algorithms (knowing how to reparse and splice efficiently in many scenarios).

### “Flat” AST Representations and Memory Locality

One more notable approach, often used in high-performance compilers, is to store ASTs in a **flat or packed format** rather than as pointer-rich object graphs. For instance, instead of having each node allocate separately on the heap and link via pointers, you can use arrays of data to represent the tree. One example is an AST stored in parallel arrays: an array of node kinds, an array of first-child indices, an array of sibling indices, etc., or a single large array of nodes where each node record contains offsets to its children. This approach can be very cache-friendly – by keeping data in contiguous memory, you reduce pointer chasing. A recent discussion referred to this as “flattening ASTs” where essentially an AST is treated similarly to an IR in SSA form, using indices instead of pointers. The benefit is that traversing the tree involves stepping through arrays (which utilize CPU caches well) rather than following pointers to random memory locations.

Such representations can be either mutable or immutable. If immutable, updating might mean creating a new array or using something like a piecewise array copy (which is complex). If mutable, it might be easier to update but then you lose persistence. Some language implementations (especially those targeting performance like JIT compilers or GPU compilers) use flat AST or IR representations for speed and compactness.

For the scope of a syntax *tree* in source analysis, a flat representation is somewhat unusual but not unheard of. One could imagine a parser that generates a vector of nodes and a vector of child links. This is not a typical approach for an external API (developers generally prefer an object model to work with), but as an internal representation it could be used.

**Trade-offs:** The flat model maximizes locality and is great for scenarios where you repeatedly traverse the whole tree (e.g., in code generation or optimization, which often iterates over the AST/IR many times). In an IDE scenario, though, you rarely traverse the entire tree blindly; you often search specific parts (like “what’s the AST node at this cursor position?” or “find all class declarations”). For those, having direct parent/child pointers or indexes might be more straightforward than working with a purely indexed structure. Also, implementing a flat structure can be like writing your own miniature memory manager and can complicate tree algorithms.

However, it’s worth noting that some modern systems like Roslyn have taken steps in this direction: the Roslyn green nodes are already optimized to be compact (many are value-packed, some derive common base classes), and the caching of child positions is a form of optimizing locality. Rust’s `rowan` and `cstree` essentially treat the green tree in a very flat way: green nodes are uniform (dynamically typed by a kind tag) and stored in a way that child relationships are index-based or offset-based internally. This dynamic/untyped nature is a bit like a flat structure because you don’t generate a separate class for each AST node type – you use a code (token kind or node kind) and a list of children. This simplifies allocation and allows using generic storage.

In summary, flat or packed representations are a niche but important alternative when raw performance (especially memory throughput) is paramount. They often sacrifice some ease-of-use and flexibility, but they align well with how CPUs work.

## Implementation Guidelines for a Python Syntax Tree Framework

Designing a syntax tree framework in Python brings its own challenges and opportunities. Python is a high-level, dynamically-typed language with automatic memory management (garbage collection) and no real compile-time optimizations for custom data structures. Therefore, we should tailor our approach to Python’s strengths (ease of use, flexibility) while mitigating weaknesses (speed and memory overhead of Python objects). Below are guidelines and patterns drawn from the research, adapted to a Python context:

### Choosing an Architecture

**Prefer Immutability for Public API:** Even though Python is not traditionally used for massive-scale IDE parsing, adopting an immutable tree model will greatly simplify reasoning about the tree and enable potential reuse of nodes. A **red-green tree architecture can be implemented in Python**, but we must be mindful of object overhead. An alternative is to implement a *single-tree persistent AST* with explicit support for parent links via a facade (essentially a simplified red-green). One approach is to mimic Roslyn’s idea:

* **Green nodes**: pure data containers (e.g., using Python tuples or lightweight classes) for syntax, with no parent reference and perhaps storing just length/width and child references.
* **Red nodes**: wrapper objects that hold a reference to a green node plus parent and tree context.

This could be done by defining classes like `GreenNode` and `SyntaxNode` (red). The `SyntaxNode` methods (like `.children` or `.parent` or `.get_text_range()`) would use information from the green node and possibly cached context to provide the needed interface. The green nodes could be implemented as Python tuples for minimal overhead (e.g., `(kind, width, children_tuple)`), or as dataclasses with `__slots__` to avoid the overhead of `__dict__`. By using tuples for children, we ensure they are immutable (assuming we never mutate that tuple of child references).

**Structural Sharing in Python:** We won’t get pointer-level deduplication automatically like Roslyn (which interns identical nodes globally). We can, however, implement interning manually for certain common elements. For example, we can keep a dictionary of interned green token nodes keyed by (kind, text, trivia) so that requesting a token returns a cached one. This mimics Roslyn’s token cache. Python strings are already interned in some cases (identifiers) and reused by the interpreter, so identical keywords might already share the underlying string, but making their node objects identical too could save memory. Be careful to only intern truly *identical and context-free* pieces (like individual tokens). Larger green subtrees could also be cached (perhaps using a hash of their structure as a key), but this gets complex and might not be worth it unless performance proves problematic.

**Parent Pointers:** In Python, if we implement red nodes with parent references, we will create reference cycles (a parent refers to child and child refers back to parent). The Python garbage collector can handle cycles, but they might delay collection and add overhead. One strategy is to use **weak references** for parent pointers on red nodes. Python’s `weakref` module allows an object to refer to another without increasing its refcount, so if the only references to a red subtree are weak (from its parent), that subtree can be collected. For instance, each `SyntaxNode` (red) could store a weak reference to its parent node. The root’s parent would be `None`. This way, if you drop all external references to a whole red tree, it can be GC’d, even if parent<->child cycles existed (because the cycle is weak at the parent link).

**Laziness:** Python can leverage laziness similar to Roslyn’s approach. We can design `SyntaxNode.children` as a property that generates red children on the fly from green children. For example, when you access `node.children`, the code will iterate over the green node’s children and wrap each in a `SyntaxNode` with `parent=self`. It could cache this list in the `node` (perhaps in a hidden attribute) so that subsequent access returns the same Python list of child nodes. To avoid strong reference cycles, those child nodes might have weakrefs back to their parent as discussed, or the parent might not hold a strong reference to the list after returning it. However, caching a list of children in the parent is typically fine because parent and children should be collected together anyway if the parent is out of scope.

One might also implement an iteration protocol instead: define `__iter__` on `SyntaxNode` to yield child `SyntaxNode`s one by one, constructing them on the fly. But then multiple iterations would recreate children repeatedly – not ideal. Better to generate once and cache. An LRU cache could be considered for children if memory is a concern (auto-discarding red nodes that haven’t been used recently), but that’s probably overkill initially.

**Absolute Positions:** Since green nodes carry widths, a red node can compute its absolute position by summing the widths of all preceding siblings plus the parent’s position. This can be done recursively or by storing it. Roslyn computes positions on the fly as you navigate down the tree. In Python, computing on the fly should be fine for most cases (the depth isn’t huge in typical code). If needed, we can cache the position in the red node at creation time to avoid re-summing for repeated requests. Because red nodes are thrown out on edits, any cached position remains valid for that red node’s lifetime (the tree is immutable).

### Memory Management and Performance Tips

Python objects have more overhead (each object has reference counts, type info, etc.). To mitigate this:

* Use **slots** in classes like `GreenNode` or `SyntaxNode` to avoid the per-object dictionary. This can halve memory for many objects.

* Consider using tuples or namedtuples for green nodes since they are immutable and compact. A namedtuple for a green node might have fields like `(kind, text, width, children)`. But keep in mind deep recursion on Python tuples for large trees might impact recursion limits; using iterative algorithms or limiting recursion is wise.

* Avoid creating objects for trivial structures. For example, Roslyn uses struct for tokens – in Python, we can’t have real value types easily, but we can represent tokens simply as interned strings or small objects. Perhaps represent a token’s green node as just the string itself if the token kind is identifiable from the string (not always true due to identifiers vs keywords, etc.). Alternatively, a token could be a tuple like `('IDENTIFIER', 'foo', trivia_before, trivia_after)` for the green layer and the red layer just refers to that. This is a design trade-off between clarity and performance.

* Use flyweight patterns for trivial values: e.g., single-character punctuation nodes could be singleton objects (there’s no need to allocate a new comma token node every time if we can reuse one).

**Garbage Collector considerations:** Python’s GC works with refcounting primarily, collecting cycles occasionally. In a red-green design, green nodes might live long (potentially through many versions if we keep them or intern them), whereas red nodes will be created and dropped on each edit. We should avoid situations where a lot of abandoned red nodes stick around in cycles. The weakref for parent should alleviate that – when the last external reference to a red subtree is gone, the weakly-held parent doesn’t count, so the cycle breaks and all those objects can be collected immediately. We should test the memory behavior: create a tree, drop it, ensure memory frees (to avoid memory leaks).

### API Design and Usability

A syntax tree API in Python should feel pythonic but also be efficient for the typical use cases (traversals, pattern matching, transformations):

* **Node classes or one class?** Roslyn uses a full type hierarchy (different classes for each syntax node type), whereas Rust’s rowan uses a single homogenous node type with a kind tag. In Python, having a distinct class for each grammar rule could be overkill and heavy (lots of classes, and Python method dispatch is not super fast). A simpler approach is to have just a couple of classes: one for *internal nodes* and one for *tokens*. We can differentiate node types by an enum or string code (`node.kind` attribute). This is akin to the dynamically typed approach in Rust analyzer. For example, `node.kind` might be `"IfStatement"` or `"ReturnStatement"` etc., and based on that you know how to interpret the children (first child is 'if' keyword token, second is condition expression, etc.). We can generate this mapping from the grammar. This makes the visitor implementation easier: you write a single `visit(node)` function that switches on `node.kind`, rather than having dozens of methods.

* **Visitor pattern:** We can provide a base visitor class or simply encourage using `isinstance`/`kind` checks. Python’s dynamic nature means users might not strictly need the classic Visitor pattern; they can traverse the tree with a simple loop or recursion and use `if node.kind == 'Something': ...`. However, for convenience, we could implement a visitor that uses method naming convention: e.g., `visit(node)` in base class finds `visit_<kind>(self, node)` if it exists. This is similar to how the built-in `ast` module in Python works (it has `NodeVisitor` with `visit_Name`, `visit_Call`, etc.). Implementing such a mechanism for our syntax nodes would improve ergonomics.

* **Tree modification API:** If we allow modifications (to produce new trees), we should do so in an immutable fashion. For example, a method `node.replace(child, new_child)` would return a *new* `SyntaxNode` where that replacement is done, leaving the original unchanged. Under the hood, this would create a new green node for the parent with children list adjusted, and then wrap it in a new red node. Essentially this is constructing a new version of the tree. This is exactly how Roslyn’s `WithX` methods work (e.g., `node.WithExpression(newExpr)` returns a new node). We can implement something similar: for each node kind, provide functions to create a new node of that kind given possibly modified children. If our design doesn’t have separate subclasses, this might be a generic function like `replace_node(node, **kwargs)` that knows how to build a new green node of the same kind with certain children replaced.

* **Incremental update strategy:** If the framework is for an interactive environment, we might integrate with text edits. One approach: maintain a mapping from text positions to syntax nodes (or token), to quickly find what node an edit touches. But computing that mapping globally is heavy. Alternatively, mimic Roslyn: provide an API where given an old root and a text diff, the parser can reuse old green nodes and return a new root. This requires the parser to be incremental-aware. In Python, implementing a full incremental parser might be beyond scope, but at least we can allow partial reuse: e.g., if the edit is inserting a space or a comment (trivia) which doesn’t affect the tree structure, we could just adjust a token’s trivia rather than reparse everything.

### Thread Safety and Concurrency in Python

Due to the Global Interpreter Lock (GIL), Python doesn’t truly run bytecodes of two threads simultaneously in one process. So thread-safety is somewhat moot for computationally heavy operations (they won’t run in parallel anyway). However, multiple threads could still interleave and see partial changes if one thread is building a tree while another is reading it. Using immutability avoids any need for locks: if a thread has a reference to a `SyntaxNode`, that node and its whole green subtree will never change under it. So if another thread produces a new tree version, it will be a separate set of objects. As long as you don’t mix them up, they won’t conflict. This is a strong reason to enforce that the tree objects are effectively frozen.

If one were to use multiprocessing (separate processes) for analysis, then you’d typically need to serialize the tree (e.g., send it via pickle). A red-green tree might not be trivially pickleable unless you define custom reduce logic (because of the weakrefs and possibly recursive structure). But you can always serialize by just sending the text or some diff, so not a big issue.

One should also consider that Python’s memory management might behave differently from .NET’s. In .NET, the large number of small objects was mitigated by generational GC tuning. In Python, the refcounting means as soon as a red node is not referenced, it’s freed (cycles aside). That is good for memory locality perhaps (no long-lived garbage). But if you create and destroy a lot of objects rapidly (like red nodes on every keystroke), Python might fragment the heap or spend time in allocations. We could measure this, but if it becomes an issue, one could try object pooling (though Python doesn’t provide a straightforward allocator control, we could reuse SyntaxNode objects from a pool theoretically). However, object pooling in Python might not be worth it due to the GIL and the overhead of Python-level management.

Given Python’s speed, we also want to avoid *extremely deep recursion* in pure Python for traversal or copying, as Python has a recursion limit (typically 1000). A deeply nested AST (like a thousand-deep nested expression) could hit that. We may need to implement traversal in an iterative way if such depths are possible in the language.

### Metadata and Annotations

In compilers, after parsing the syntax tree, later phases often attach additional info to AST nodes (type info, symbol references, etc.). In an immutable tree, we cannot directly add fields to existing node objects without breaking the model. Options:

* **Side Tables:** Maintain a dictionary mapping node (or node id) to metadata. For example, a `dict` keyed by node identity (id or perhaps the green node object since green nodes are shared for identical structure) to some analysis result. This decouples the analysis data from the tree. The downside is it’s a bit unwieldy to pass around, and if nodes can be collected, the keys might become invalid unless you use something like `WeakKeyDictionary` that drops entries when the node is gone.
* **Wrapper Objects:** Alternatively, one could create a new wrapper that contains both the syntax node and, say, an annotation. But that tends to proliferate wrapper classes and is not ideal.

Given the focus is on the syntax tree framework itself, I would lean towards not storing metadata in the tree. Instead, encourage users to keep analysis results separate. If needed, we could provide an *augmentation API* where users can attach metadata via a key, and internally it uses a side table or attaches it to the red node (since red nodes are short-lived, maybe not that). Possibly, one could attach to green nodes by an intern key because green nodes are shared: e.g., give each green node a unique ID (maybe assign an incrementing ID when creating new green nodes) and then use that ID in a dict for metadata. That way it remains valid across versions as long as that green node persists in the new tree.

However, a caution: if you start storing analysis info keyed by green nodes, when an edit occurs that doesn’t disturb a certain subtree, the new tree will reuse the old green subtree, and you automatically get the metadata still mapped to it (which might be great because the semantic info is still valid if the subtree didn’t change!). This is actually a potential feature: persistent semantic analysis. But ensuring validity might be complex (some semantics can change even if syntax stays same, e.g., if a variable declaration elsewhere changed scope). So probably not attempt automatically carrying semantic info across versions beyond what the user explicitly handles.

### Putting It All Together (Example)

Let’s sketch a brief example in pseudocode to illustrate how a Pythonic red-green implementation might look:

```python
# Enum of syntax kinds
from enum import Enum
class SyntaxKind(Enum):
    NUM_LITERAL = 1
    ADD_EXPR = 2
    # ... other kinds

# Define a lightweight GreenNode structure
class GreenNode:
    __slots__ = ('kind', 'width', 'children')  # children is a tuple of GreenNode or None for tokens
    def __init__(self, kind, width, children=()):
        self.kind = kind
        self.width = width  # total text length of this node's span
        self.children = children  # tuple of GreenNode; for tokens, children=()
    def __repr__(self):
        return f"GreenNode({self.kind}, width={self.width})"

# Red (Facade) Node
class SyntaxNode:
    __slots__ = ('_green', '_parent', '_index', '_abspos')
    def __init__(self, green: GreenNode, parent=None, index_in_parent=0, abspos=0):
        self._green = green
        self._parent = parent  # weakref to parent if needed
        self._index = index_in_parent  # index in parent's children tuple, to help position calc
        self._abspos = abspos  # absolute offset in the file for this node's start
    @property
    def kind(self):
        return self._green.kind
    @property
    def parent(self):
        return None if self._parent is None else self._parent()  # if stored as weakref
    @property
    def children(self):
        # Lazily wrap green children as SyntaxNode
        result = []
        pos = self._abspos
        for i, child_green in enumerate(self._green.children):
            child_abspos = pos  # current position
            child = SyntaxNode(child_green, parent=weakref.ref(self), index_in_parent=i, abspos=child_abspos)
            result.append(child)
            pos += child_green.width  # increment position by the child's width for next
        return result
    def get_text(self, source_text):
        # Assuming we have the original source text, return substring for this node
        return source_text[self._abspos : self._abspos + self._green.width]
    # Possibly methods like replace, etc.
```

This code is illustrative: it shows how a red `SyntaxNode` could carry an absolute position and reference its green node. The `children` property wraps green children in red nodes on the fly. We’d likely want to cache the `children` list for performance (store it as a hidden attribute after first computation). We might also want a method to find a child by kind or to traverse.

To handle tokens vs internal nodes, we might decide that tokens are just GreenNodes with `children=()`. A `NUM_LITERAL` kind green node might hold its lexeme text in another field (we might include a `value` or `text` in GreenNode for tokens). Alternatively, have a separate `GreenToken` class. But for simplicity, we can encode token text as part of the `GreenNode` maybe via an attribute or by convention that leaf nodes of certain kinds correspond to tokens.

**Builders and Parsing:** Constructing these nodes by hand is tedious, so a *builder pattern* is useful. We could write a `GreenNodeBuilder` that has methods `start_node(kind)`, `add_token(kind, text)`, `finish_node()` which uses a stack to build GreenNodes (similar to Rust’s `GreenNodeBuilder`). The builder would accumulate children and compute widths as it finishes nodes. This would be used by the parser. Once parsing is done, we get a `GreenNode` root which we can wrap in a `SyntaxNode` and return to the user.

**Incremental parsing:** We can attempt incremental parsing by comparing old and new text in the parser. For example, if using a PEG or recursive descent, we could use a heuristic: at the position of edit, skip to a safe restart point (like start of a statement), reuse the old green nodes for preceding parts unchanged, parse the changed part anew, then try to reuse following parts if the structure allows. True incremental parsing is complex, but even reusing unchanged top-level declarations in a module (like, if you edit one function, maybe other functions can be reused as green subtrees) can give a performance win. We can implement it at a coarse granularity first: e.g., parse into a list of top-level elements; when text changes, do a diff on the text or tokens to see which top-level elements changed, reuse the others’ green nodes in the new tree. This is simpler than arbitrary mid-function edits but it’s a start. As we refine, we could narrow the region of reparse using the old tree structure.

**Testing and Performance:** We would write tests to ensure that after an edit, the new syntax tree shares objects with the old one appropriately (i.e., identity comparison on sub-nodes). Also test that parent pointers and positions are correct.

### Summary of Guidelines

* **Immutability First:** Keep the core tree nodes (green) immutable and separate from navigation logic (red). This simplifies many aspects (concurrency, versioning).
* **Optimize Pythonic Overhead:** Use `__slots__`, intern frequently repeated elements, and maybe use tuples for leaf nodes to reduce Python object overhead.
* **Lazy and Cached Computations:** Only compute red nodes, child lists, or absolute positions on demand, and cache results where feasible to avoid repeated work. But use weak references or careful scoping for caches to avoid memory leaks.
* **API Ergonomics:** Provide easy ways to walk and query the tree (iteration, visitors) and to create new versions (copy with modification). Mirror some patterns from Roslyn (like factory functions or `.withX` methods) to make tree manipulation intuitive.
* **Balance Complexity:** Recognize that Python may not handle extremely large trees as well as systems languages – so choose battles. It might be acceptable to reparse a whole function on an edit rather than implement a very fine-grained incremental algorithm that complicates the code, because the absolute performance might be dominated by Python execution anyway. Optimize where it counts (like not reconstructing huge unchanged subtrees), but don’t over-engineer for micro-optimizations that won’t show through Python’s interpreter overhead.
* **Threading:** Use immutability to your advantage so you rarely need locks. If using worker threads or processes for analysis, consider the cost of duplicating trees vs. the convenience of just sharing them read-only.

## Case Studies of Tree Implementations in Practice

To solidify our understanding, let's examine how a few real-world systems implement their syntax trees. We will look at Roslyn (C#) as the canonical example of Red-Green architecture, Swift's libSyntax which applied a similar idea, and Rust's analyzer (Rowan/cstree) which further evolved the concept. We’ll also briefly note how these compare to an older approach like JetBrains’ IntelliJ PSI (which represents a contrasting mutable model).

### Roslyn (C#) – Red-Green Pioneered

Roslyn, Microsoft’s .NET compiler platform for C# and VB, was the trailblazer of the red-green architecture. As discussed, Roslyn’s design goals for syntax trees were ambitious, aiming for immutability, completeness, and incremental updates. The solution they devised is exactly as described in our analysis: a green tree for persistence and a red tree for public API.

**Implementation details:** Roslyn’s green nodes are classes like `SyntaxNode` (for non-terminals), `SyntaxToken`, and `SyntaxTrivia` (for extra whitespace/comments) in the internal implementation. Each green node knows its length in characters, an enum “kind”, and references to child green nodes. They do not know their parent. The entire source file is one green tree (e.g., a `CompilationUnit` green node). The red nodes in Roslyn are the exposed `SyntaxNode` API that users see (somewhat confusingly, the public `Microsoft.CodeAnalysis.SyntaxNode` is the red one, internally it wraps a green called something like `GreenNode`). These red nodes have properties like `.Parent`, `.Span` (which gives the absolute position and length), `.ChildNodes()` to enumerate children, etc., which they compute from the green structure.

**Performance tricks in Roslyn:** We already covered some: red tokens are structs to cut object count, common greens are interned/cached aggressively (keywords, punctuators), weak references for red nodes to ease GC, and prefix sum arrays for positions in long child lists. Additionally, Roslyn’s green node implementation uses object pooling in certain places. For example, parsing often involves creating many temporary intermediate nodes that get immediately combined into bigger nodes; Roslyn uses *node reuse* where possible and also has some pool for syntax trivia builder, etc., to reduce allocations. Another interesting aspect: Roslyn doesn’t even create a red node for every token when scanning the file. The scanner directly produces green tokens (possibly from cache), then the parser produces green nodes. Red nodes are only created if something asks for them. This means if you never actually navigate to a certain part of the tree, the system might never instantiate those red wrappers – saving time.

**Thread safety and reuse:** Since Roslyn trees are immutable, they are shared freely. In Visual Studio, the same green tree nodes might be shared between the compiler and the IDE features (class outline, refactoring tools, etc.) to save work. Each might have its own red tree or traverse via green if needed. Roslyn’s documentation notes that any `SyntaxNode` (red) can be safely read on multiple threads. However, they do caution that one should not keep references to red nodes across edits without expecting them to be outdated. Instead, an edit gives you a new tree (or you explicitly call `.ReplaceNode` which gives a new tree).

**Lessons learned:** Roslyn’s approach was very successful but not without cost. Early performance tests showed high GC overhead, which required the optimizations we mentioned. The complexity of maintaining two parallel structures is non-trivial – it was a significant engineering effort. The benefit is an extremely powerful API for code analyzers and refactoring tools. Many analyzers can operate by simply comparing syntax trees (taking advantage of immutability to easily compute diffs or caches keyed by node identity). Also, features like formatting or code generation can produce new trees by reusing pieces of old ones (they have methods to e.g. take an existing node but with different children, which under the hood just plucks the green node of the original for reuse).

### Swift’s libSyntax – Adopting Red-Green in C++

The Swift programming language initially used a more traditional compiler AST for compilation, but a separate library called **libSyntax** was introduced to model the syntax, especially to support tooling (like Swift’s IDE and source tooling). LibSyntax explicitly took inspiration from Roslyn: it implements a **red-green tree in C++**.

**Design:** In libSyntax, a **green tree** (they call them RawSyntax nodes in some documentation) represents the concrete syntax. These are reference-counted objects (since C++ doesn’t have GC, they use `shared_ptr`/`intrusive_ptr` style memory management). Green nodes are immutable once created; if you want to change one, you create a new one (they are often also value-typed under the hood to enable sharing easily). Each green node holds its kind, text (for tokens), and children. Notably, the green tree can represent *invalid syntax* as well (incomplete constructs) to support error recovery in parsing – just as Roslyn’s does (Roslyn might create “missing” nodes for things omitted, etc.). On top of the green, Swift has **Syntax (red) nodes** which are value types (structs in C++) that act as wrappers pointing to an underlying green node plus some contextual info (like parent pointer or source location). Because they’re structs, they are cheap to create and destroy (no heap alloc per red node). In fact, the Swift team made the red nodes value types so that they could be formed and passed around easily without worrying about ownership (the underlying green is reference-counted). This is a clever way to avoid the GC issue: C++ doesn’t have a GC to collect unused red nodes, but by making them temporary value objects, you typically don’t heap allocate them at all.

**Usage in Swift tools:** With libSyntax, Swift can do things like parse a file into a libSyntax tree and use it for syntax highlighting, code folding, etc. There’s also a mechanism to go from the libSyntax tree to the Swift AST (which is more abstract and used for actual compilation). They keep them separate in part because the Swift AST drops a lot of syntax details (like parentheses, commas, etc.), whereas libSyntax keeps all that (making it “lossless” syntax tree akin to a full CST). This separation echoes the idea that red-green trees can be used to maintain a full-fidelity CST for IDE purposes, and then you may have a simpler AST for the compiler proper. This two-tree approach (CST vs AST) is orthogonal to red-green (you could have a persistent AST too), but here Swift essentially has a *triplet*: Green CST, Red CST facade, and a separate AST.

**Performance:** The libSyntax developers reported that representing everything (including every punctuation) as nodes did inflate memory, but they also found it manageable with the sharing and value-type reds. Swift’s approach likely interns common tokens (like Roslyn) – a simple example, all instances of “func” keyword in source can point to one green token node for “func” with no trivia. Swift also used a unified binary format for green nodes to make them small (bit-packing like Roslyn).

One difference is concurrency: because they use reference counting, as long as those are atomic, the green nodes can be shared across threads safely (similar to Rust’s approach). The red struct nodes being value types and often recreated as needed means if two threads want to read the tree, they either each have their own red wrapper or pass them by copy, so no contention.

**Incremental updates:** Swift has an incremental parsing system known as *Swift Syntax Parsing* (with an API for incremental syntax tree reconciliation). It can take an old libSyntax tree and a new edited source and try to reuse subtrees. This again mirrors Roslyn’s capabilities. Under the hood, they likely do a diff or use node IDs to identify unchanged regions.

**Lessons:** Swift’s adoption validated that the red-green concept is language-agnostic. By implementing it in a manual memory management environment, they proved it’s viable outside of GC languages. Using value types for red nodes is a smart alternative to having a GC for them – something to consider in other systems as well (for instance, one could imagine a Python C extension where red nodes are just lightweight C structures). The trade-off remains memory vs speed, but Swift decided the benefits to tooling and correctness (having an immutable, always-valid tree) outweighed the costs.

### Rust Analyzer (Rowan and CSTree) – Refining the Model

Rust’s compiler itself does not use red-green trees (it uses a traditional AST for compilation that is thrown away each compile, and it doesn’t need to preserve trivia). However, the Rust community, inspired by these ideas, built **rust-analyzer** – an IDE backend providing incremental parsing, type checking, etc. Rust-analyzer introduced a library called **Rowan** for syntax trees, which implements a red-green tree in Rust. Rowan’s design is quite interesting because it pushes the idea of *dynamic typing* for the syntax tree: there is one `SyntaxNode` type for all nodes, distinguished by a numeric kind and (at the Rust type level) by what language it belongs to.

**Rowan’s design:**

* Green nodes are called `GreenNode` and green tokens `GreenToken`. They are immutable and reference-counted (using Rust’s `Arc`, atomic refcount). Each green node stores a kind (as a `SyntaxKind` enum – u16 as per dev.to article) and a list of children (which can be nodes or tokens). The width (text length) is stored too. They do not have parent or offset, as expected.
* Red nodes in Rowan are of type `SyntaxNode`. Internally, a `SyntaxNode` is essentially a pair of an `Arc<GreenNode>` and a pointer to a specific position within that green node (Rowan uses some unsafe trick to allow a red node to refer to a specific green node and know its parent chain without storing them all; essentially it stores the `Arc<GreenRoot>` and an index path or something to the subnode). In safe terms, you can think of red `SyntaxNode` as holding the green node and the context (parent chain) necessary to get e.g. its ancestors. They provide parent navigation etc. via that.
* One twist: Rowan was built to allow *multiple languages* or grammars to use it by parameterizing the syntax kind. It means you can use Rowan to implement a syntax tree for any language by defining your SyntaxKind enum and grammar.
* Another twist: Rowan’s red API allows building a *typed AST view* on top of the untyped CST. That is, you can have something like `ast::IfExpr` struct that wraps a `SyntaxNode` but provides typed getters (like `.condition() -> Option<Expr>`). Internally it just checks that the node’s kind is `IF_EXPR` and then picks the right child etc. This is done by the codegen of the Rust analyzer: it reads a grammar spec and generates these AST wrapper types. But they are just for convenience; the underlying tree is still the same. This way, they marry the benefits of a strongly-typed AST with the flexibility of a uniform tree underneath.

**Performance choices in Rowan:** Rowan originally recreated red nodes on the fly for traversals (similar to Roslyn’s lazy approach) and did not cache them strongly. The reasoning was to keep the API simple and not manage lifetimes of red nodes too much (since in Rust, Arc<GreenNode> ensures the green data stays alive, red nodes are more like lightweight handles). However, it turned out that *recreating red nodes repeatedly can be a performance issue* for deep traversals. So an alternative library **cstree** forked Rowan and made some adjustments:

* cstree *persists red nodes* once created: meaning if you ask for child 5 of the root, it will store it and return a reference, instead of constructing a new SyntaxNode each time. This improves traversal speed at the cost of memory (you keep red nodes around).
* To support this, cstree uses an internal reference-count on the whole tree and interior references for nodes, which allows it to give out references (\&SyntaxNode) safely in Rust rather than owned nodes. It also thereby made SyntaxNode `Send + Sync` so multiple threads can share the same red tree safely.
* cstree also allows attaching custom data to red nodes. This is something we considered earlier: e.g., one could attach an identifier for a node or analysis info. They likely implement this by storing a side-map keyed by node or by embedding a small data field in the node struct (perhaps using a slot for user data).
* Both Rowan and cstree deduplicate strings (for token text) to save memory. Instead of every identifier token carrying its string, they intern all strings in a global arena and the green token just has a pointer or index to the interned text. This is important especially in Rust where a `String` allocation per token would be heavy. (In our Python case, we rely on Python strings which are also interned for identifiers and such by the interpreter in many cases or at least reused from the source, but this general principle stands.)

**Rust analyzer’s incremental abilities:** With this tree, rust-analyzer can do things like incremental name resolution and type checking. The syntax tree is used to quickly figure out what changed in the source and what needs re-analysis. The fact that the green tree is persistent means if the user changes one function, the rest of the file’s tree is identical (the same Arc<GreenNode> pointers) and the analyzer can potentially skip reprocessing unchanged parts. They likely compute hashes of subtrees to quickly identify identical subtrees between versions.

**Lesson:** The Rust experience shows how one can adapt red-green trees with the strong guarantees of Rust’s memory safety and no garbage collector. They also highlight the trade-off between *always reconstructing red nodes on the fly (lower memory, but slower traversal)* vs *keeping red nodes (faster reuse, but higher memory and complexity)*. The cstree variant leans toward keeping red nodes around to optimize performance, effectively moving a bit closer to a traditional AST in usage (since now you *do* have an object graph you can hold and traverse freely, rather than ephemeral view nodes).

Rust’s approach also demonstrates a nice pattern of separating the concerns of **CST vs AST**: they keep the immutable concrete syntax tree for correctness and incremental updates, and layer a more convenient AST facade with types for ease of use in semantic logic. This is analogous to red/green itself, but here both layers are immutable; one is just more abstract.

### Other Notable Implementations

* **IntelliJ IDEA (PSI Trees):** JetBrains IDEs (for Java, Kotlin, etc.) use a platform called PSI, which stands for Program Structure Interface. PSI trees are a kind of AST that includes all detail (so really a CST) and are **mutable**. They allow in-place modifications and are integrated with the editor’s document model. When you type, the PSI tries to perform an *incremental parse* of just the modified file region. Essentially, IntelliJ’s parser infrastructure can produce a partial AST for the changed text and then merge it with the existing AST. The PSI nodes have parent pointers and all the usual AST conveniences, but modifications are under the hood carefully done to mimic immutability from the perspective of user code (they don’t just expose arbitrary pointers for you to monkey with). They also maintain *stamps/versions* so they can detect if a PSI node is from an outdated file version. This system was developed before red-green became known, and it works reliably, but it’s quite complicated. It’s also not as thread-safe; usually, IntelliJ uses a single UI thread for most PSI operations or read/write locks to protect AST during modifications. This underscores that while the immutable approach (red-green) adds complexity in the data structure, the mutable incremental approach pushes complexity into synchronization and partial parsing logic. JetBrains has managed it, but it's a significant engineering effort.

* **Microsoft TypeScript:** The TypeScript compiler has an incremental mode for the language service. It doesn’t use a red-green tree; rather, it parses the file and then does a diffing of the AST based on text ranges to reuse certain AST subtrees when possible. The AST is mutable (they have parent pointers and you can even mutate it with transformer APIs). But the language service typically reparses each time a file changes (though it can skip parsing files that didn’t change). There was an effort to make a more incremental parsing, but due to the relatively fast performance of parsing in JS and the complexity, they often just reparse the whole file on edit. Still, they do create a new tree, not modify the old one, for each edit snapshot, which is conceptually more like persistent (they just don’t bother reusing internal nodes because GC will clean the old ones and parsing is fast enough for typical file sizes).

* **Oil shell’s Lossless Tree:** Mentioned in the Reddit discussion, the Oil shell (a Unix shell) has a "lossless syntax tree" where they capture all whitespace and comments. It’s somewhat similar to a green tree concept. However, I believe Oil’s implementation might not specifically use red/green; it might simply have a concrete tree that can round-trip source, and then separately an AST for execution. The mention in Reddit suggests Oil’s author was exploring red-green and found it interesting but thought it mainly helped with IDE interactivity (which Oil doesn’t need as much).

* **Academic and Other**: There are plenty of academic papers on *persistent data structures*, including trees. Many functional languages’ compilers (like Elm or Haskell GHC) actually don’t do fine-grained AST persistence for editing – they recompile from scratch on changes (though GHC has incremental compilation, it’s at module level). There’s research on *incremental computation* which could in theory allow reusing previous computation results if the AST changes slightly (like self-adjusting computation). That’s beyond scope, but those techniques could complement an incremental AST by also persisting analysis results keyed by the structure (somehow invalidating only the parts affected by changes).

## Conclusion

In designing your Python syntax tree framework, the experiences of these systems should guide you. The Red-Green architecture (and its relatives) show that **investing in an immutable, persistent tree can yield big dividends** in correctness and flexibility for tooling. The cost in memory can be managed with careful implementation and is often justified by the simplicity of not having to handle mutable state issues. However, the right choice always depends on context: if you need maximum performance for single-pass compilation, a simpler AST might do. If you target rich IDE features, red-green (or at least a persistent CST) is worth it.

**Key Takeaways:**

* **Immutability & Persistence** are powerful for incremental workflows – enabling reuse of most of the tree across versions and safe concurrent usage.
* **Structural Sharing** is the technique that makes persistence efficient, and it requires careful separation of state that changes vs state that doesn’t (hence width vs absolute position, parent pointer being out-of-band, etc.).
* **Memory Trade-offs** are real – expect higher memory usage, roughly proportional to making two of everything in red-green (though clever tricks like interning can win some back). Plan to mitigate with interning, weakrefs, and possibly pooling.
* **Complexity** moves from parse-time to runtime: implementing a red-green might be more complex than a simple AST, but using it (for the end user of the API) is easier/safer. In a mutable AST, implementing is easy but every use-site must be careful about changes.
* **Python considerations:** Emulate proven patterns but adapt to Python’s constraints. Write plenty of tests for memory leaks (cycles) and performance in Python to ensure your design is actually beneficial given the interpreter overhead.

With a solid architecture in place, your framework will enable advanced features like on-the-fly code analysis, refactoring tools, or even live coding environments, all built on a syntax tree that can *efficiently morph* as the user types, without losing its integrity or eating all the memory. By learning from Roslyn, Swift, Rust, and others, you can implement a syntax tree in Python that is modern, robust, and scalable for your needs.

**Appendix A: Simplified Code Example (Python Red-Green)**

```python
# Enum for syntax kinds
from enum import Enum
class Kind(Enum):
    NUMBER = 1
    PLUS_TOKEN = 2
    ADD_EXPR = 3
    # ... other kinds as needed

# Green Node classes
class GreenNode:
    __slots__ = ('kind', 'children', 'width')
    def __init__(self, kind, children=()):
        self.kind = kind
        self.children = tuple(children)  # immutable tuple of GreenNode or GreenToken
        # Compute width: sum of child widths (or length of token text if token)
        if children:
            self.width = sum(child.width for child in children)
        else:
            self.width = 0  # tokens might override this

class GreenToken(GreenNode):
    __slots__ = ('text', 'width', 'kind')
    def __init__(self, kind, text):
        self.kind = kind
        self.text = text
        self.width = len(text)
        self.children = ()  # no children

# Red Node (SyntaxNode facade)
import weakref
class SyntaxNode:
    __slots__ = ('_green', '_parent', '_start')
    def __init__(self, green, parent=None, start=0):
        self._green = green
        self._parent = weakref.ref(parent) if parent else None
        self._start = start  # absolute position of this node in the source
    @property
    def kind(self):
        return self._green.kind
    def parent(self):
        return self._parent() if self._parent else None
    def children(self):
        # Generate red children from green children
        offs = self._start
        result = []
        for child in self._green.children:
            node = SyntaxNode(child, parent=self, start=offs)
            result.append(node)
            offs += child.width
        return result
    def text(self, source):
        # assuming source is the full original text
        return source[self._start : self._start + self._green.width]

# Example usage:
# Build a tree for expression "1+2"
one_token = GreenToken(Kind.NUMBER, "1")
plus_token = GreenToken(Kind.PLUS_TOKEN, "+")
two_token = GreenToken(Kind.NUMBER, "2")
expr_green = GreenNode(Kind.ADD_EXPR, children=[one_token, plus_token, two_token])
# Wrap in red:
root = SyntaxNode(expr_green)
for child in root.children():  # traverse children
    print(child.kind, child.text("1+2"))
```

This example shows how you might build a simple expression `1+2` with an `ADD_EXPR` green node having three children. The red `SyntaxNode` when asked for children produces SyntaxNode wrappers for `1`, `+`, and `2`. The `text` method uses the stored start offset and the width to slice the original source string.

In a real implementation, you’d likely automate building such trees via a parser, and have more helper methods on SyntaxNode (like `find_child_by_kind` or nicer iteration). Also, caching children and using **iter** could be implemented for convenience.

**Appendix B: Performance Data**

* In Roslyn, red-green trees roughly doubled the number of objects allocated versus a traditional AST. *“This scheme ends up creating up to twice as many small objects as a normal parse tree would”*. The team mitigated this by making around half of those objects (tokens) structs to reduce heap allocations.
* Roslyn’s incremental parser can reuse \~90% of nodes or more on small edits. Edits typically required rebuilding *O(log n)* of the nodes (for example, editing inside a deeply nested construct rebuilds that chain of ancestors, but not the rest).
* Memory overhead for immutable vs mutable can be measured by comparing, say, an AST of a large file. If a mutable AST took X MB, a red-green might take 1.5–2X MB in worst case. However, due to sharing, if you consider multiple versions, the red-green might be *overall* more memory-efficient when holding multiple versions. Also, interning of greens can save memory if the file has many repeated tokens (like many `end` in a script, etc.).
* In Rust’s Rowan, benchmarks indicated that creating and dropping red nodes frequently was a bottleneck for full-tree traversals, which led to the cstree fork that improved iteration speed by retaining red nodes. This suggests that in Python, we should also be careful about overhead in creating many short-lived objects during traversal – caching child nodes in the parent could be beneficial to avoid Python function call overhead repeatedly.
* Pure persistent data structures (like Clojure’s collections) often show about 20-30% memory overhead for structural sharing pointers, but can be comparable in speed for read operations, slower for writes (since writes allocate new structure). For trees, updates are typically O(depth) for persistent vs O(1) for mutable in-place. If depth is moderate, this is fine (e.g., replacing a node in a tree with depth 20 is trivial).
* Zippers have overhead proportional to the path length for carrying context. Access at focus is O(1). If you were to move focus every element in a list of n, with a zipper you’d pay O(n) overall plus the cost of rebuilding at the end maybe O(n) — similar order as just rebuilding once, but with the benefit of localized changes and possibly better reusability of unaffected parts.

These data points reaffirm that an immutable incremental approach is often a win for real-time systems (IDE), whereas for batch processing, the overhead is not always worth it.
